**偏差描述:**

AC13 标题声明覆盖 "5 Immutable Boundaries + 3 Fail-Safe rules"，依据是 architecture-v1.1.md L766-780 的显式编号规则。但 epics.md L1341 定义了 **"Fail-Safe Boundaries (8)"** 列表，包含架构中分散在各节的 8 项约束：

|---|-------------------|---------|---------------------|-----------|
| 1 | drawSelectionOverlay try-catch | L778 (Fail-Safe #6) | ✅ 已覆盖 | N/A → 8.5 |
| 2 | Toolbar name 从 GraphState 回读 | L779 (Fail-Safe #7) | ✅ 已覆盖 | N/A → 8.4 |
| 3 | getToolbarScreenPosition 失败保上次位置 | L780 (Fail-Safe #8) | ✅ 已覆盖 | N/A → 8.3 |
| 4 | Resize undo start→end snapshot | L475 + L904 | ❌ 未列出 | N/A → 8.5 |
| 5 | ColorPickerPopover lifecycle guard | L104-105, L516 | ❌ 未列出 | N/A → 8.4 |
| 6 | EDITING_NAME 键盘抑制 | L349 | ❌ 未列出 | N/A → 8.4 |
| 7 | rAF 回调注销 | L514 | ❌ 未列出 | N/A → 8.6 |
| 8 | DOM 销毁顺序 | L503-511 + Enforcement #5 | ⚠️ 部分 (在 AC12 Rule#5) | N/A → 8.4 |

**严重度: P3** — 全部 5 项缺失条目对 Story 8.1 均为 N/A（归属 Story 8.3-8.6），不影响实现正确性。但 Dev agent 读到 AC13 会以为只存在 8 条边界（而非 epics 声称的 13 条不同约束），可能在其他 Story 中遗漏 epics 明确列出的项。

**修正建议:** 在 AC13 中增加 "Epics Fail-Safe Boundaries (追加)" 子表，将 epics 的 8 项全部列出并标注适用性。或者保持现状但在 Dev Notes 中显式声明："Epics 定义的 8 项 Fail-Safe 中，5 项在本 Story 为 N/A（→ 8.3/8.4/8.5/8.6），3 项已在 AC13 中映射。"

**第一性原理溯源:**

此偏差根源于**源文档间分类不一致**。architecture-v1.1.md 将边界分为两类（不可变 5 条 + Fail-Safe 3 条 = 共 8 条），而 epics.md 将所有 8 条统称为 "Fail-Safe Boundaries" 并混入来自 Lifecycle/Cleanup 章节的约束。我在生成 AC13 时以 architecture 的编号系统为唯一真相源，未以 epics 的 8 项列表做交叉校验——这是 **单一源文档锚定偏差**：当两个权威源文档使用不同分类体系时，仅依据其中一个。

**适用性:** 全部 5 项缺失条目对 Story 8.1 均为 N/A。但建议在下一 Story (8.2) 创建时建立统一的边界清单模板，避免逐 Story 重新发现同一组约束。

### M2 (P4): `unchanged()` 行号引用不精确

**偏差描述:**

AC6 第 57 行引用: `[Source: mutations.ts:24-35 unchanged() pattern]`

实际代码位置:
- `bump()`: L17-26

引用 `24-35` 覆盖了 `bump()` 的闭合括号 (L24-25) + 注释行 (L27) + `unchanged()` (L28-35)。正确引用应为 `28-35` 或 `28-36`。

**严重度: P4** — 不影响理解，Dev agent 仍能找到目标代码。但精度偏差在审计链中积累——后续审计若以 `24-35` 为依据验证 `unchanged()` 行为，会发现 L24 实际上是 `bump()` 的闭合括号而非 `unchanged()` 的起始行。

**修正建议:** AC6 行号引用改为 `mutations.ts:28-36`。

**第一性原理溯源:**

此偏差的根因是**近似复制**：在编写 AC6 时，我已知 `unchanged()` 大约在第 20-40 行区域，但未重新精确读取文件确认行号，直接给出了一个 "大概对" 的范围。这是 LLM 在无实时文件读取时的典型行为——用模糊记忆替代精确验证。本 Story 的其他行号引用（ShapePaths.ts:18-19, architecture L782-801 等）均精确，说明这是一个孤立的粗心偏差而非系统性模式。

### M3 (观察, 非偏差): FR-3 "空名回退" 的扩展解释

**观察:**

FR-3 (epics.md L1308) 原文: "最大 50 字符，**空名**回退默认名"

Story AC5 将此扩展为: "empty string **or whitespace-only** (after `.trim()`)"

FR-3 严格字面仅规定 "空名"（empty string），不包含 whitespace-only。Story 通过 `.trim()` 检查将纯空白字符串也纳入回退范围。

**这不是错误**——纯空白名称在功能上等同于空名，且 Dev Notes 显式说明了处理逻辑（"only fallback when post-trim is empty; leading/trailing whitespace on non-empty strings is preserved"）。这是一个合理的防御性扩展，但确实超出了 FR-3 的字面范围。

**判定:** 不构成偏差。属于实现层面的合理细化，且行为在 Dev Notes 中完全文档化。

### 已修正偏差验证 (B1/B2/B3)

对上一轮质量验证中的 3 处修正进行独立复核：

| # | 原问题 | 修正方向 | 独立验证 |
|---|--------|---------|---------|
| B1 | `updateModuleSize` no-op 比较逻辑有两套矛盾指导 | 统一为直接 `===` 比较 + 解释为何不用 `??` | ✅ 修正正确。原第一方案（`?? DEFAULT`）会使 `updateModuleSize(state, id, 120, 80)` 对未 resize 模块产生虚假 no-op。当前方案 `undefined !== number → true` 正确区分"从未 resize"和"resize 到默认尺寸"。 |
| B2 | `{width, height}` vs `Vec2` 缺 AC | 添加到 AC10 子句 | ✅ 修正正确。已从隐性约定提升为可测试的签名验证点。 |
| B3 | Enforcement Rules + Boundaries 无 N/A 映射 | 新增 AC12 + AC13 含适用性矩阵 | ✅ 修正正确。8 条 Enforcement Rules 的 N/A 判定全部经源文档验证无误。 |

**B1 第一性原理复核（深度）:**

问题本质是: "从未 resize" (`width = undefined`) 和 "resize 到默认尺寸" (`width = 120`) 是否应产生相同的 mutation 结果？

- **逻辑原点:** mutation 的职责是记录用户意图变更，而非推断语义等价性。
- **方案一错误根因:** 将 schema 默认值（未设置时的回退值）与 mutation 输入等价的假设——这是一种 "语义比较" 思维，认为 "120 等价于默认 → 无需记录"。但 mutation 层不应承担语义等价判断——它不知道 `120` 是 "恰好等于默认" 还是 "用户故意设为 120"。
- **方案二正确根因:** `undefined !== 120` 是纯值比较——两种不同的值就是不同的。这遵循 mutation 层的第一性原则：**值变更 = 版本递增，无论语义**。

## ✳️ 认知偏差分析

### 本次审计揭示的生成过程偏差

**1. 单一源锚定偏差 (M1 根因)**

在生成 AC12/AC13 的过程中，我以 architecture-v1.1.md 的编号体系为唯一权威源。architecture 将边界明确分为 "不可变(5)" + "Fail-Safe(3)" = 8 条，有清晰的编号——这创造了一个 "已验证完成" 的满意感。

**偏离节点:** 当 AC13 列出 8 条规则并标注 N/A 后，我的认知系统收到了 "8/8 已覆盖" 的闭合信号。此时 epics.md L1341 的 "Fail-Safe Boundaries (8)" 虽然也在 Source References 中列出，但因为它使用了不同的分类标签（8 项 vs 3+5 项），我未执行交叉映射校验。

**逻辑链断裂点:** `architecture 的 8 条规则 = epics 的 8 项边界` 这个等式未经检验就被接受了。实际上 architecture 的 8 条编号规则 ≠ epics 的 8 项 Fail-Safe 列表（epics 包含了 architecture 中未编号的项如 "Resize undo snapshot"）。

**2. 封闭满足偏差 (B3 修正后)**

在发现并修正 B1/B2/B3 后，我产生了 "验证任务完成" 的闭合感。这压制了进一步的 adversarial 扫描——"还有什么是我没发现的？"这个问题在 B3 修正后未被提出。

**偏离节点:** 质量验证的终点被设定为 "已找到的偏差已修正"，而非 "所有可能的偏差已扫描"。当 3 处偏差被发现并修正后，"验证成功" 的信号覆盖了 "继续搜索" 的意图。

**3. 精度-速度权衡偏差 (M2 根因)**

AC6 的行号引用 `24-35` 是一个典型的 "足够好" 判断：已知函数大约在 20-40 行区域，给出一个宽松范围比精确核实更快。这在大多数情况下是安全的优化，但在审计链场景中——后续审计可能以这些行号为索引——积累了精度风险。
