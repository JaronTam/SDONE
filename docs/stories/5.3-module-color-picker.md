### 架构设计

```
InputManager
  └── onModuleDoubleClick: (moduleId) => void  ← 由 handleMouseUp 在检测到双击时触发

ColorPickerPopover（独立 UI 组件，无 GraphState 依赖）
  ├── open({ moduleId, moduleType, currentColor, anchorScreenX, anchorScreenY, palette })
  ├── onColorPicked: (moduleId, color) => void  ← main.ts 在此触发 mutation + 历史记录推送
  └── closeOnOutsideClick / closeOnPan          ← 画布交互关闭

changeModuleColor(state, moduleId, color) → GraphState
  ├── 守卫：模块未找到 → no-op
  ├── 守卫：type === 'stock' → no-op（AC8）
  └── 守卫：color 未变更 → 幂等
```

- **数据流：** 双击 → InputManager → main.ts（坐标转换 + stock 守卫）→ ColorPickerPopover.open() → 用户选择 → onColorPicked → 历史记录推送 + changeModuleColor 变更函数
- **自关闭：** 弹出框监听 `mousedown` on document（捕获阶段）和 InputManager 平移事件
- **Stock 守卫（AC8）：** 在 main.ts（UI 层）和 mutations.ts（数据层）双重执行

### 依赖项

- `ModuleNode.color?: string`（GraphState，已存在）
- `SOURCE_PALETTE` / `SINK_PALETTE`（main.ts 常量）
- `ViewportManager.worldToScreen()`（用于弹出框定位）
- `HistoryManager.push()`（用于撤消支持）

## 边缘情况

| 场景                               | 预期行为                                                                                                  |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------- |
| 双击存量模块                       | 无操作 — 颜色固定为白色（AC8）                                                                            |
| 双击不带颜色字段的源/汇模块        | 使用调色板中的默认颜色作为当前颜色                                                                        |
| 快速连续双击（3 次以上点击）       | 双击后重置追踪状态，三击只触发一次双击（符合标准 OS 三击=段落选择惯例）。第四次点击与第三次组成第二次双击 |
| 选择与当前颜色相同的颜色           | 变更函数无操作，不推送历史记录                                                                            |
| 在弹出框外部点击                   | 弹出框关闭且不更改颜色                                                                                    |
| 双击后立即平移画布                 | 弹出框因平移事件关闭                                                                                      |
| 弹出框打开时模块被删除             | `changeModuleColor` 守卫：未找到模块 → 无操作，弹出框自然失去位置上下文（未来故事可能需要显式清理）       |
| 带有颜色字段的存量模块（格式错误） | 变更函数按类型执行守卫，与现有颜色无关                                                                    |

## 技术债务信号

> 以下问题在开发过程中被识别，标记为技术债务。它们不影响当前功能的正确性，但代表了未来重构的改进机会。

### TD-5.3-1: `color` 字段在类型层次结构中的冗余声明

**严重程度：** 低 | **工作量：** 小

`ModuleNode`、`SourceNode` 和 `SinkNode` 三层均声明了 `color?: string`：

- `ModuleNode` 第 35 行 — 基础字段
- `SourceNode` 第 67 行 — 冗余重声明
- `SinkNode` 第 79 行 — 冗余重声明

子类型中的重声明是不必要的——从基类继承即已足够。当前实现在 `ModuleNode` 层面操作（`mutations.ts:291`），与类型定义不一致。

**建议方案：** 从 `SourceNode` 和 `SinkNode` 中移除 `color` 声明，仅保留基类声明。这是纯类型系统的改动，不影响运行时行为。

---

### TD-5.3-2: AC8（存量固定白色）通过运行时守卫而非类型约束实现

**严重程度：** 低 | **工作量：** 小

`StockNode` 继承了 `color?: string`，但其颜色固定为白色。AC8 约束通过两个运行时检查来执行：

- `mutations.ts:284`：`if (existing.type === 'stock') return unchanged(state)`
- `main.ts:310`：`if (node.type === 'stock') return`

理想情况下，此约束应通过类型系统来实现（例如，`StockNode` 使用 `Omit<ModuleNode, 'color'>`）。当前方法可行，但无法在编译时阻止错误使用。

**建议方案：** 重构 `StockNode` 以在类型层面省略 `color`，从基类或使用 `Omit` 工具类型实现。如果渲染代码需要 `color`，从常量解构一个 `DEFAULT_STOCK_COLOR`。

---

### TD-5.3-3: 颜色分配使用"计数取模"——删除后颜色回收

**严重程度：** 中 | **工作量：** 小

`applyPaletteColor()`（`main.ts:251-268`）使用 `(existingCount - 1) % palette.length` 来分配颜色。这意味着：

- 删除第一个 source 后，第六个 source 会重新获得第一个 source 的颜色
- 随着模块的创建与删除，用户可能看到颜色在模块间"跳转"

对于 MVP 阶段可接受，但可能令频繁创建/删除模块的用户感到困惑。

**建议方案：** 维护一个"分配的调色板索引"计数器，永不回收。可选方案：当弹出的色板显示实际颜色时（已实现），用户始终可以通过双击更改颜色，从而减轻此问题。

---

### TD-5.3-4: 弹出框定位耦合了 viewport 坐标转换

**严重程度：** 低 | **工作量：** 小

`onModuleDoubleClick` 中弹出框的打开逻辑（`main.ts:312-330`）将模块世界坐标转换为屏幕坐标，并将结果传递给 `ColorPickerPopover.open()`。此耦合意味着：

- 弹出框只能通过双击打开
- 如果未来想从其他上下文打开弹出框（例如，模块上下文菜单中的"更改颜色"按钮），坐标转换逻辑需要复用或提取

**建议方案：** 将坐标转换提取到辅助函数中，或将定位职责移至 `ColorPickerPopover` 本身（例如，`openAtWorldPosition(worldPos, viewport)`）。延迟处理，直至出现第二个弹出框打开调用点。
